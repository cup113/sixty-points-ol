# 牌局编排台是纯客户端工具，交付契约是一份 JSON

> **状态**：已被 ADR-0025 取代 —— 新手引导上线后，编排台与牌局故事管线整体退役删除。本 ADR 记录的是它存续期间的架构决定。

作者在 `/studio` 里输入种子、把一副牌从头打到尾、每一步旁边写说明，导出一个 JSON；下游「规则演示」页读这份 JSON 渲染。整条链路不经过服务端：牌局由引擎的纯函数（`replayStory` → `dispatch`）生成，草稿存浏览器 localStorage，导出/导入是唯一的数据交换方式。理由有三条。**其一，能力已经就位**：引擎零依赖且已打进客户端 bundle（`/rules` 教程一直就在组件里直接调它），所以「种子 → 一副牌」不需要任何服务端权威；反过来说，为一个单人写作工具新建 SQLite 表 + REST 接口 + 鉴权，成本全花在与玩法无关的地方。**其二，需求本来就不含跨机器复现**：作者要的是「关掉页面还能接着写」，localStorage 足够，真要挪窝就导出 JSON。**其三，只有一份事实**：牌面、赢家、墩分、结算都由引擎现算，作者只写「为什么」，所以网页上的讲解不可能与规则漂移。

契约本身有三条硬规定，都是为了「网页上的牌面与讲解将来不会对不上」。**牌面冗余存证**：`deal.hands` / `deal.originalKitty` / `deal.kitty` / `trump` / `contract` / `summary` 都写进 JSON，下游渲染只读它们，种子只用于草稿重建与溯源 —— 哪天引擎或 RNG 实现变了，老讲解也不会变味（转换脚本落地时同步加一个测试，把「存下来的牌面」与「现场回放的结果」对一遍）。**种子↔牌局钉在仓库里**：用自带的 `mulberry32`（不是服务端那个每次现取的 `cryptoRng` —— 线上牌局每副不可复现正是它要的性质，这里恰好相反），一副草稿共用一个 RNG 实例，跨「三家不叫重发」连续推进，回放才能一步步对齐。**说明不进回放输入**：`notes` 与 `actions` 平行存放，敲字时不会重放整副牌；导出时才把两者合成一条条 `{type, …, note}`。

两处刻意的实现取舍。**出手先试回放再落地**（`append.ts`）：界面上把按钮变灰只是第一道提示，真正的判定是把新动作接到末尾回放一遍、引擎说不行就一个字节都不写 —— 所以导出的动作序列天然合法，测试再回放一次只为锁死。**撤销按整份快照整块回退**：不做「说明与动作按下标对齐」那种一改就错位的逻辑，代价是每步快照一份小对象（上限 200 步，可忽略）。

代价：`.svelte.ts` 里的 rune 代码跑不了 `node:test`，所以判定逻辑一律抽成纯函数（`replay.ts` / `append.ts` / `annotate.ts` / `export.ts` / `draft.ts` 都有测试），`studio.svelte.ts` 只剩接线与响应式；交互过程本身（点牌、翻页手感）只能由作者本人点一遍。另外 `/studio` 虽然随站点部署、线上靠 URL 可打开，但它不在玩家流程里挂任何链接 —— 它写的是访问者自己的浏览器存储，服务端一无所知。
